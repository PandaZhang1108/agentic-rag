# Dense Top5 与 Cross-Encoder Reranker A/B 实验

## 实验问题

固定同一份 Milvus Dense 索引，比较：

- A：Dense 直接取 Top5。
- B：Dense 先取 Top10，再用 `BAAI/bge-reranker-base` 重排并取 Top5。

评测使用 `domain/evalset.jsonl` 中带 `relevant_ids` 的 25 道开发题。模型在 CPU
运行；模型与 Embedding 的首次加载属于热身，不计入逐题延迟。

## 结果

| 指标 | Dense Top5 | Dense Top10 + Cross-Encoder Top5 | 变化 |
|---|---:|---:|---:|
| Recall@5 | 0.7533 | 0.8067 | +0.0533 |
| MRR@5 | 0.6713 | 0.7693 | +0.0980 |
| P50 延迟 | 34.1 ms | 584.6 ms | +550.5 ms |
| P95 延迟 | 43.3 ms | 778.9 ms | +735.6 ms |

Dense Top10 的候选 Recall@10 为 0.8467，相比 Dense Top5 有 0.0933 的候选空间，
说明 Reranker 不是完全没有可发挥的资料。

具体收益包括：`q018` 的 Recall 从 0 提升到 1，`q021` 从 0.3333 提升到
0.6667。但 `q001`、`q002`、`q023` 的首个正确页面排名下降。`q010`、`q016`、
`q017` 等题的完整正确资料没有进入 Top10，Reranker 无法补回候选集之外的内容。

## 第一轮决定（`bge-reranker-base`）

**当前不接入正式 Agent。**

预先设定的接入条件是：候选空间至少 0.05、重排后 Recall 不下降、Recall 或 MRR
至少提升 0.05，并且新增 P95 延迟不超过 500 ms。本次质量条件通过，但新增 P95
延迟为 735.6 ms，超过止损线。

这不是说 Cross-Encoder 没有效果，而是当前 `bge-reranker-base + CPU` 组合的收益
不足以覆盖延迟成本。以后只有在改用更小模型、硬件加速或离线批处理后，才重新测试；
不能直接根据本轮结果宣称 Reranker 已上线。

## 候选数量补充实验

保持模型、数据集、索引、最终 Top5 和 CPU 不变，只把 Dense 候选数量改成
`6/7/8/10`：

| candidate_k | Candidate Recall | Reranked Recall@5 | Reranked MRR@5 | 新增 P95 | 判断 |
|---:|---:|---:|---:|---:|---|
| 6 | 0.7667 | 0.7667 | 0.7513 | 383.3 ms | 延迟通过，质量提升不足 |
| 7 | 0.7667 | 0.7467 | 0.7493 | 490.4 ms | 延迟通过，但 Recall 低于基线 |
| 8 | 0.8067 | 0.8067 | 0.7693 | 657.4 ms | 质量通过，延迟失败 |
| 10 | 0.8467 | 0.8067 | 0.7693 | 735.6 ms | 质量通过，延迟失败 |

`k=6` 会丢掉让 `q018` 改善的候选；`k=7` 仍未找回 `q018`，并在重排时把
`q020` 的部分正确资料挤出 Top5。`k=8` 与 `k=10` 的最终质量相同，说明第 9、10
名候选没有继续贡献，但 `k=8` 的 CPU P95 仍然超过止损线。

因此，单纯缩小候选数量无法让当前模型同时满足质量与延迟要求。下一轮只有更换更小的
多语言 Reranker、量化模型或使用可用的 GPU，才构成有意义的新实验条件。

## 小模型补充实验

保持数据集、Dense 索引、CPU、`candidate_k=8` 和 `final_k=5` 不变，只将
Reranker 替换为 `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`。本机实际加载的
模型包含 `117,641,089` 个参数。

| 指标 | BGE Base，k=8 | MMARCO MiniLM，k=8 | 变化 |
|---|---:|---:|---:|
| Reranked Recall@5 | 0.8067 | 0.8067 | 0.0000 |
| Reranked MRR@5 | 0.7693 | 0.7560 | -0.0133 |
| Reranker P50 | 470.1 ms | 175.5 ms | -294.6 ms |
| Reranker P95 | 684.2 ms | 249.0 ms | -435.2 ms |
| 端到端 P95 | 702.9 ms | 264.8 ms | -438.1 ms |
| 新增 P95 | 657.4 ms | 226.6 ms | -430.8 ms |

小模型保持了 BGE Base 的 Recall，MRR 仅下降 0.0133，同时将新增 P95 从
657.4 ms 降到 226.6 ms。逐题对比中只有两道题的首个相关页面位置发生变化：
`q001` 从第 3 位升到第 2 位，`q012` 从第 1 位降到第 2 位；其余题的 Recall 和
MRR 与 BGE Base k=8 相同。

按照实验前设定的质量与延迟门槛，小模型结果为 `integrate`。这里的含义是
**值得进入接入与答案层回归阶段**。目前已配置化接入 `retriever.asearch()`：
Milvus 先取 8 块，Reranker 重排后向 Agent 返回 5 块；模型在 Agent lifespan
启动阶段预加载，推理失败时记录错误并退回 Milvus 原始前 5 块。

接入后的真实入口复跑结果：

| 指标 | 接入前 Agent 基线 | 接入后 Agent |
|---|---:|---:|
| Recall@5 | 0.7333 | 0.8667 |
| MRR@5 | 0.7200 | 0.8533 |
| 多跳题 Recall | 0.4667 | 0.9333 |
| 工具选择准确率 | 0.8667 | 0.8333 |
| 答案四维均分 | 0.9125 | 0.9375 |
| P50 延迟 | 2872.3 ms | 4299.9 ms |
| P95 延迟 | 13643.8 ms | 8363.1 ms |

30 道 Agent 题全部成功。答案评分沿用正确性、完整性、忠实性、相关性四维标准，
由 Codex 辅助逐题复核，覆盖率为 100%。`q006` 的示例类型标注不严谨；`q021`
错误否定了应用级全局依赖，
这是生成层仍需保留的坏例。工具选择下降也说明 Reranker 只改资料排序，不能修复模型
是否调用工具的决策。

## 路由与生成修复后的回归

针对上述生成错误和非 FastAPI 技术题的工具路由补充约束后，再次运行同一套 30 题：

| 指标 | 最新回归 |
|---|---:|
| 成功用例 | 30 / 30 |
| Recall@5 | 0.9467 |
| MRR@5 | 0.9280 |
| 工具选择准确率 | 0.9667 |
| 答案四维均分 | 0.9667 |

这轮同时改变了路由和生成提示词，因此只能证明当前完整版本在固定题集上的表现，
不能把提升全部归因于 Reranker。评测使用 4 并发，本地 Embedding 和 Reranker
由信号量串行保护；记录到的 p95 还包含冷启动和排队，不能解释成单请求延迟。

延迟对照不是严格的性能因果实验：两轮 Agent 运行包含不同的网络和模型生成波动。
接入后的独立 25 题检索运行中，首次并发加载两个本地模型使前 4 题达到约 5 秒，
预热后其余题约 0.64–0.99 秒；因此正式服务已改为启动阶段预加载。

## 证据边界

当前 `relevant_ids` 标注到页面 `source_id`，不是精确 chunk，因此页面命中不等于
答案所需片段一定充分。本实验只证明检索排序变化，不证明最终答案质量或线上泛化能力。
公开仓库保留两份关键原始证据：小模型逐题 A/B 位于
`eval_results/reranker-ab-mmarco-minilm-k8-20260928.json`，最新完整 Agent 回归位于
`eval_results/agent-reranker-regression-scored-20260929.json`。BGE 和候选数量的中间
试验只在本文保留汇总，避免把全部调参产物提交到作品集仓库。
